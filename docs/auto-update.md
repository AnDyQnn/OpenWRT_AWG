# Автообновление шлюза — проектный документ

> Статус: **РЕАЛИЗОВАНО** (канал обновлений 2.3.x). Ф0–Ф6 + Приложения А/Б/В/Г —
> в `main`, проверены on-device на стенде с реальным туннелем (CHECK→APPLY→COMMIT→
> ROLLBACK, сегментация L2/L3, кнопки железа, бэкапы). Документ оставлен как
> обоснование решений. Прод трогать только через бэкап + проверенный откат.

Документ описывает фичу «Обновление»: вкладку в веб-панели и механику доставки
обновлений на железо с автоматическим бэкапом, самодиагностикой и откатом.

> **Приложения** (в конце) — отдельные связанные фичи, можно делать независимо
> от автообновления:
> - **А** — раздельное туннелирование **по устройству** (тумблер «Интернет
>   напрямую/мимо VPN» у клиента, напр. телевизора);
> - **Б** — управление железом (кнопки «Перезагрузить» / «Выключить»);
> - **В** — стратегия DHCP (длинная аренда / авто-резервирование + чистка пула)
>   и разбор «резервирование ≠ VLAN»;
> - **Г** — сегментация сети / VLAN: две модели (L3-политики vs настоящий L2),
>   per-VLAN egress (интернет/VPN/только локалка), адресное пространство, карта сети;
> - **Д** — аудит прода (as-built), согласование фич с ТЗ и принцип
>   железо-агностичности («заменил 100М→1Г / 2→4 карты — ничего не поменялось»).

---

## 1. Цель

- Обновлять **код шлюза, а не перезаливать дистрибутив**: железо тянет код из
  отдельной ветки-канала и накатывает обновление поверх работающей системы.
- Никогда не ронять прод: любое обновление обратимо, откат восстанавливает
  состояние «как было» (БД/конфиги/контейнеры).
- Минимум мусора на диске после обновления.

Полный образ-дистрибутив (для **чистой заливки** нового железа) — отдельный трек,
уезжает в `release`. К in-place обновлению он отношения не имеет.

---

## 2. Базовые принципы (на них держится всё)

1. **Жёсткое разделение КОДА и СОСТОЯНИЯ.** Обновление синхронизирует только код
   (`/opt/gateway` + образы контейнеров). Состояние (см. §6) обновление **не
   трогает напрямую** — оно снимается в бэкап до наката и восстанавливается при
   откате. Только так возможен откат «как было».
2. **На проде не собираем.** `amneziawg-go` компилируется из исходников ~15 мин и
   может упасть на полпути. Железо тянет **предсобранный образ** (по digest), а не
   делает `docker build`. Сборка — только в CI и дома.
3. **Откат полностью локальный.** Не зависит от сети/интернета (управление идёт
   через сам туннель — если накат отрубит сеть, удалённо откатить не выйдет).
4. **Dead-man switch.** Если накат завис/железо ребутнулось посреди обновления —
   при старте срабатывает авто-откат по маркеру «update in progress».
5. **Идемпотентность.** Любой этап можно безопасно повторить; прерывание питанием
   не оставляет систему в полуобновлённом состоянии.
6. **Целостность артефакта.** Образ тянется по **digest** (`@sha256:...`),
   зафиксированному в манифесте обновления — это сам по себе даёт проверку
   целостности (Docker отвергнет образ с другим содержимым). webui — privileged
   контейнер с доступом к `docker.sock`, поэтому что попало грузить нельзя.
7. **Требования к хосту объявляются декларативно.** Кроме кода и состояния есть
   третья категория — то, что должно быть в самой ОС: `apt`-пакеты, включённые
   юниты, файлы-предпосылки. Они перечислены в `gateway/host-requirements.list`,
   который читают И сборка образа, И накат по каналу — единым списком, чтобы они
   не разъехались. Подробно см. §8A.

## 3. Архитектура: два трека

```
                 push в main / PR
                       │
                       ▼
        ┌──────────────────────────────┐
        │  CI (GitHub Actions)          │
        │  1. build образов             │
        │  2. pipeline-проверки + тесты │  ← тестовый VPN-конфиг как secret
        │     (поднять стек, прогнать   │
        │      linux-gw/test)           │
        └──────────────┬───────────────┘
                       │ всё зелёно?
            ┌──────────┴───────────┐
            ▼                      ▼
   ┌─────────────────┐   ┌──────────────────────────┐
   │ release         │   │ ветка-канал `upd-code`    │
   │ полный образ-   │   │ лёгкий код + VERSION +    │
   │ дистрибутив для │   │ manifest.json (digest     │
   │ чистой заливки  │   │ образов). Образы — в GHCR │
   └─────────────────┘   └────────────┬─────────────┘
                                       │ pull (авто/по кнопке)
                                       ▼
                          ┌────────────────────────┐
                          │ Железо: gateway-update  │
                          │ staging → backup →      │
                          │ apply → health-gate →   │
                          │ commit / rollback       │
                          └────────────────────────┘
```

### Ветка-канал `upd-code`
- Содержит **только то, что нужно для in-place обновления**: дерево `/opt/gateway`
  (`docker-compose.yml`, `awg/`, `dnsmasq/`, `webui/`), host-скрипты из
  `rootfs-overlay` (если меняются), `VERSION`, `manifest.json`.
- Образы в ветке **не лежат** (тяжёлые) — лежат в **GHCR**, ветка пинит их digest.
- Обновляется CI автоматически после прохождения пайплайнов (промоут из main).

## 4. CI (GitHub Actions)

Workflow `.github/workflows/build-and-release.yml` (создать в ветке `feat/auto-update`):

1. **build** — собрать 3 образа (`gateway-awg`, `gateway-dnsmasq`, `gateway-webui`).
2. **test** — поднять стек в раннере, прогнать `linux-gw/test/*` с **тестовым
   VPN-конфигом** (хранится как `secrets.TEST_AWG_CONF`, прокидывается в шаг
   как файл). Проверки: туннель встаёт, handshake, панель отвечает, базовый
   forwarding. Конфиг даёшь дома → кладёшь в Settings → Secrets.
3. **publish (только если test зелёный)**:
   - `docker push` образов в `ghcr.io/AnDyQnn/openwrt-awg/<svc>:vX.Y.Z` + по digest;
   - сгенерировать `manifest.json` (версия + digest каждого образа + changelog);
   - закоммитить код + `VERSION` + `manifest.json` в ветку `upd-code`;
   - (опционально) собрать полный образ-дистрибутив и приложить к GitHub Release.

`manifest.json` (пример):
```json
{
  "version": "2.2.0",
  "channel": "upd-code",
  "released": "2026-06-25T20:00:00Z",
  "images": {
    "gateway-awg":     "ghcr.io/andyqnn/openwrt-awg/awg@sha256:...",
    "gateway-dnsmasq": "ghcr.io/andyqnn/openwrt-awg/dnsmasq@sha256:...",
    "gateway-webui":   "ghcr.io/andyqnn/openwrt-awg/webui@sha256:..."
  },
  "min_from_version": "2.0.0",
  "changelog": "Защита туннеля от широких маршрутов; ..."
}
```

## 5. Версионирование

- Формат: **semver** `X.Y.Z` в файле `VERSION` (корень `/opt/gateway/VERSION`).
- На железе текущая версия = `/opt/gateway/VERSION` (или `/etc/awg-setup/.version`,
  чтобы переживала перезалив кода — решить при реализации, рекомендую второе).
- Сравнение: `доступная > текущая` → есть обновление.
- `min_from_version` в манифесте — нижняя граница, с которой возможен прямой
  апгрейд (если ниже — сначала промежуточная версия).
- Существующие теги `linux-gw-vX.Y` оставляем для дистрибутива; для канала
  обновлений используем чистый semver.

## 6. Состояние: что бэкапим и восстанавливаем

> **Реальной БД нет** — всё состояние это плоские файлы. Список выверен по коду
> webui и по живому серверу.

### Обязательно сохранять (потеря = поломка/разлогин/потеря доступа)
| Путь | Что это |
|------|---------|
| `/etc/amnezia/awg0.conf` | **VPN-конфиг + приватные ключи** (0600) |
| `/etc/awg-setup/.session-secret` | секрет подписи сессий (потеря → все разлогинены) |
| `/etc/awg-setup/dashboard-creds.json` | логин/пароль панели (если задан) |
| `/etc/awg-setup/dashboard-users.json` | пользователи панели (если заданы) |
| `/etc/awg-setup/filter/rules.json` | **главное состояние**: split/block/groups/hosts |
| `/etc/awg-setup/orig-config.conf` | исходный загруженный VPN-конфиг (0600) |
| `/etc/awg-setup/filter/orig-allowedips.txt` | исходные AllowedIPs (для обратной карты) |
| `/etc/awg-setup/user-mode` | режим vpn/off, заданный пользователем |

### Желательно сохранять (не критично, но приятно)
| Путь | Что это |
|------|---------|
| `/var/lib/misc/dnsmasq.leases` | аренды DHCP (клиенты сохранят IP) |
| `/etc/awg-setup/weekly-report.json` | накопленная статистика отчёта |
| `/etc/awg-setup/wan-gw`, `wan-port` | детект WAN (восстановится сам, но пусть) |

### НЕ бэкапить (генерируется из кода/rules.json или эфемерно)
- `/etc/awg-setup/filter/{access-rules,access-sets,block,reservations}.{txt,conf}`,
  `direct.list`, `direct-cidrs.list` — **производные**, webui пересоберёт из
  `rules.json`. (Можно включить в бэкап для побайтового отката — безвредно.)
- `/etc/awg-setup/split-default.json` — шаблон, приходит **с кодом**.
- `/run/awg-*`, `/run/awg-stats/*` — tmpfs, эфемерно (счётчики failover/recovery).
- `/etc/awg-setup/.installed` — маркер.

### Практическое правило
Состояние крошечное (килобайты). Чтобы не ошибиться — **бэкапим целиком**:
```
/etc/awg-setup/   (весь каталог)
/etc/amnezia/     (весь каталог)
/var/lib/misc/dnsmasq.leases
```
Восстановление при откате — **целиком и побайтово** (это корректно обрабатывает
миграции схемы: откат вернёт старый формат `rules.json` как был).

## 6A. Бэкап и восстановление (фундамент — сейчас ОТСУТСТВУЕТ)

> На текущем проде **бэкапов нет вообще**. Это базовый механизм, на котором
> держится откат обновлений, и он же ценен сам по себе: регулярный бэкап
> конфигов/настроек/состояния защищает от любой потери (кривой апдейт, сбой диска,
> ошибка пользователя). Делаем его **первым** — обновления только переиспользуют.

### Единый механизм
Один скрипт снимает/восстанавливает состояние §6. Его зовут из трёх мест:
1. **`[BACKUP]` обновления** (автоматически перед накатом);
2. **периодический таймер** (ежедневно, независимо от обновлений);
3. **вручную из UI** («Создать бэкап» / «Скачать» / «Восстановить» / «Загрузить»).

Бэкап = один tar-архив со снимком состояния + метаданными (версия, дата, причина).
Лежат в `/opt/gateway-backups/`. Ретеншн — последние `K` (§8, дефолт 3); ручные и
предобновленческие можно помечать «keep», чтобы не вычищались.

### `gateway-backup.sh`
> `linux-gw/rootfs-overlay/usr/local/bin/gateway-backup.sh`
```sh
#!/bin/sh
# Снимок состояния шлюза. $1 = причина (update|cron|manual), $2 = метка (напр. версия).
set -eu
BK=/opt/gateway-backups
WLOG=/var/log/awg-watchdog.log
reason="${1:-manual}"; label="${2:-$(cat /etc/awg-setup/.version 2>/dev/null || echo unknown)}"
ts=$(date '+%Y%m%d-%H%M%S')
dir="$BK/${label}-${ts}"
_log(){ printf '%s gateway-backup: %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >> "$WLOG"; }
mkdir -p "$dir"

# Состояние §6 (бэкапим целиком — оно крошечное). Отсутствующие пути пропускаем.
tar czf "$dir/state.tar.gz" \
    --ignore-failed-read \
    -C / \
    etc/awg-setup \
    etc/amnezia \
    var/lib/misc/dnsmasq.leases 2>/dev/null || true

# Метаданные бэкапа.
cat > "$dir/meta.json" <<EOF
{"version":"$label","reason":"$reason","created":"$(date -Iseconds)","ts":"$ts"}
EOF
# Контрольная сумма — целостность при восстановлении.
sha256sum "$dir/state.tar.gz" | awk '{print $1}' > "$dir/state.sha256"
_log "бэкап создан: $dir (причина=$reason)"
echo "$dir"
```

### `gateway-restore.sh`
> `linux-gw/rootfs-overlay/usr/local/bin/gateway-restore.sh`
```sh
#!/bin/sh
# Восстановление состояния из бэкапа. $1 = путь к каталогу бэкапа.
# ВАЖНО: восстанавливаем ПОБАЙТОВО и поверх (миграции схемы откатываются корректно).
set -eu
dir="$1"; WLOG=/var/log/awg-watchdog.log
_log(){ printf '%s gateway-restore: %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >> "$WLOG"; }
[ -f "$dir/state.tar.gz" ] || { _log "ERR нет $dir/state.tar.gz"; exit 1; }

# Проверка целостности перед распаковкой (защита от битого/подменённого архива).
want=$(cat "$dir/state.sha256" 2>/dev/null || echo)
have=$(sha256sum "$dir/state.tar.gz" | awk '{print $1}')
[ -n "$want" ] && [ "$want" != "$have" ] && { _log "ERR sha256 не сошёлся для $dir"; exit 1; }

# Снимаем «before-restore» страховку текущего состояния (на случай отмены).
gateway-backup.sh restore-safety pre-restore >/dev/null 2>&1 || true

# Распаковка поверх корня. tar перезапишет файлы состояния как были в бэкапе.
tar xzf "$dir/state.tar.gz" -C / && _log "состояние восстановлено из $dir"
# Поднять стек заново, чтобы сервисы перечитали восстановленные конфиги.
( cd /opt/gateway && docker compose up -d ) >/dev/null 2>&1 || true
_log "восстановление завершено"
```

> Эти же два скрипта обслуживают `[BACKUP]`/`[ROLLBACK]` обновления — отдельной
> логики для отката писать не нужно. Откат состояния = `gateway-restore.sh` на
> бэкапе, снятом перед этим накатом.

### Периодический бэкап
- `gateway-backup.timer` → ежедневно (напр. 03:30) `gateway-backup.sh cron`.
- Дёшево (килобайты), даёт точку отката даже без обновлений.

### UI (вкладка «Обновление» или отдельный блок «Резервные копии»)
- Список бэкапов (версия, дата, причина, размер), «Скачать» (отдать tar).
- «Создать бэкап сейчас», «Восстановить из…», «Загрузить бэкап» (импорт tar).
- «Восстановить» помечает страховку pre-restore, чтобы отменить неудачное восстановление.

### Шифрование (на подумать)
`/etc/amnezia/awg0.conf` содержит **приватные ключи**. Если бэкапы скачиваются/
хранятся вне устройства — рассмотреть шифрование архива (парольная фраза в UI).
Локально на устройстве — права 0600 на каталог бэкапов.

## 7. On-device: машина состояний обновления

Скрипт `gateway-update.sh` (host, `/usr/local/bin/`). Каждый этап логируется в
журнал событий и обновляет статус во вкладке «Обновление».

> **Цикл «одно поколение отката».** В любой момент на диске лежит ровно одна
> страховка — образ + бэкап состояния предыдущей версии. Чистим старое **в начале
> следующего обновления**, не раньше. Порядок шагов критичен (см. ниже почему):
> сначала делаем НОВУЮ страховку, потом сносим СТАРУЮ.

```
[CHECK] ──► есть обнова? ──нет──► выход (статус: актуально)
   │ да
   ▼
[PREFLIGHT]  место на диске, docker info, не идёт ли уже апдейт (lock)
   │ ok                         │ fail ─► статус: не начато, причина
   ▼
[BACKUP]  (1) состояние §6 → /opt/gateway-backups/<from>-<ts>/ (+ /opt/gateway)
          (2) текущие РАБОЧИЕ образы → docker tag ...:rollback
              ⚠ это ПЕРЕБИВАЕТ старый тег :rollback (он указывал на N-2);
                образ N-2 после переноса тега становится «осиротевшим» —
                его и почистит следующий шаг.
          (3) маркер /etc/awg-setup/.update-inprogress (from, to, ts)
   │ ok                         │ fail ─► статус: не начато (бэкап не удался)
   ▼
[CLEANUP]  снести осиротевший образ прошлого поколения (бывший N-2) +
           dangling-слои + кэш сборки. НЕ трогаем свежий :rollback (=N-1)
           и :latest. Подчистить бэкапы сверх ретеншна K. (см. §8)
   │ ok                         │ fail ─► не критично, продолжаем (лог WARN)
   ▼
[APPLY]   rsync staging → /opt/gateway; docker pull@digest (из manifest);
          docker compose up -d
   │ ok                         │ fail ─► [ROLLBACK]
   ▼
[HEALTH-GATE]  самодиагностика §9 (таймбокс ~90с)
   │ ok                         │ fail ─► [ROLLBACK]
   ▼
[COMMIT]  снять маркер; обновить версию (current → N); запомнить «last good»;
          :rollback ОСТАЁТСЯ = N-1 (страховка до следующего обновления);
          статус: обновлено до vX.Y.Z
   │
   ▼ конец

[ROLLBACK]  восстановить /opt/gateway из бэкапа; docker tag :rollback → :latest;
            восстановить состояние §6 ПОБАЙТОВО из бэкапа этого же обновления;
            docker compose up -d; прогнать health-gate ещё раз (прод вернулся?);
            снять маркер; статус: ОШИБКА на этапе <X>, откат выполнен;
            уведомление во вкладке + в журнале событий
```

### Почему порядок именно BACKUP → CLEANUP (а не наоборот)
`docker system prune -af` считает «неиспользуемым» любой образ, на который не
ссылается **запущенный контейнер** — наличие тега не спасает. Образ `:rollback`
специально не запущен, значит для `prune -af` он мусор и был бы снесён.

Поэтому:
- чистку делаем **не вслепую** (`prune -af` запрещён до COMMIT) и **только после
  того, как пометили новую страховку**;
- на CLEANUP уже существует свежий `:rollback` (=N-1, работавшая до наката версия),
  и мы сносим лишь то, что осиротело от **прошлого** цикла (N-2). Так страховка
  всегда жива: и во время наката, и после COMMIT — вплоть до следующего обновления.

### «last good» для отката
- `:rollback` (образ) + последний бэкап в `/opt/gateway-backups/` = пара для отката.
- При `[ROLLBACK]` берём бэкап, созданный в `[BACKUP]` **этого же** обновления.
- Кнопка «Откатиться на предыдущую» в UI работает, пока живы `:rollback` и его
  бэкап (т.е. между обновлениями) — спасает от багов, всплывших ПОСЛЕ health-gate
  (медленные/периодические — health-gate их за 90с не ловит).

### Dead-man switch (отдельно от inline-отката)
- При `[BACKUP]` ставится маркер `/etc/awg-setup/.update-inprogress`.
- При `[COMMIT]`/`[ROLLBACK]` маркер снимается.
- **На загрузке** systemd-юнит `gateway-update-guard.service` (Before сети/compose):
  если маркер есть → значит апдейт не завершился (зависание/потеря питания/потеря
  доступа) → **авто-откат** из последнего бэкапа.
- Дополнительно: после `[APPLY]` арм-таймер на N минут; если `[COMMIT]` не
  наступил (например, потеряли доступ и не подтвердили) — авто-откат.

## 8. Очистка мусора (по запросу: «не засирать сервак»)

**Модель:** держим **одно поколение** отката. Чистим **на шаге `[CLEANUP]`**
текущего обновления — то есть сносим страховку ПРОШЛОГО цикла уже после того, как
сделали страховку нового (см. §7, «почему BACKUP → CLEANUP»).

**Запрещено:** `docker system prune -af` «как есть» — снесёт `:rollback`, т.к. на
него не ссылается запущенный контейнер (тег не спасает). Используем **целевую**
чистку: dangling-слои + кэш сборки + явное удаление осиротевшего образа N-2.
`prune -af` единым махом допустим только если СОЗНАТЕЛЬНО отказываемся от отката
(сбросили `:rollback`) — тогда пути назад нет.

Что чистим на `[CLEANUP]`:
1. Осиротевший образ прошлого поколения (бывший `:rollback`=N-2, тег уже перенесён
   на N-1) — удалить по ID.
2. `docker image prune -f` — dangling-слои.
3. `docker builder prune -f` — кэш сборки (актуально для домашней сборки).
4. Staging-папка `/opt/gateway-staging` (после успешного APPLY больше не нужна).
5. Бэкапы сверх ретеншна K: `ls -1dt /opt/gateway-backups/*/ | tail -n +$((K+1)) | xargs rm -rf`.

Ретеншн (`K` бэкапов, по умолчанию 3) и число поколений образов (по умолчанию 1) —
в конфиге обновлений (§10).

### Готовый скрипт `gateway-prune.sh`
> `linux-gw/rootfs-overlay/usr/local/bin/gateway-prune.sh`. Вызывается из
> `gateway-update.sh` на шаге `[CLEANUP]`. Идемпотентен, безопасен для прода.

```sh
#!/bin/sh
# Целевая очистка после смены поколения. НЕ трогает :latest и :rollback.
# $1 = ID образа(ов) прошлого поколения для удаления (опционально, через пробел).
WLOG=/var/log/awg-watchdog.log
KEEP_BACKUPS="${GW_KEEP_BACKUPS:-3}"
BK=/opt/gateway-backups
_log(){ printf '%s gateway-prune: %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >> "$WLOG"; }

# 1) Явно переданные осиротевшие образы прошлого поколения (бывший :rollback).
for img in "$@"; do
    [ -n "$img" ] || continue
    docker rmi "$img" 2>/dev/null && _log "удалён старый образ $img"
done

# 2) Висячие слои (безымянные, ни на что не указывают) — :rollback это НЕ заденет.
docker image prune -f >/dev/null 2>&1 && _log "image prune (dangling) ok"

# 3) Кэш сборки.
docker builder prune -f >/dev/null 2>&1 && _log "builder prune ok"

# 4) Staging.
rm -rf /opt/gateway-staging 2>/dev/null

# 5) Бэкапы сверх ретеншна.
if [ -d "$BK" ]; then
    old=$(ls -1dt "$BK"/*/ 2>/dev/null | tail -n +$((KEEP_BACKUPS+1)))
    [ -n "$old" ] && echo "$old" | xargs rm -rf && _log "удалены бэкапы сверх $KEEP_BACKUPS"
fi
_log "очистка завершена"
```

> ⚠ Скрипт сознательно **не** делает `docker system prune -a`. Если когда-нибудь
> добавишь его — только под флагом и только когда `:rollback` уже сброшен.

## 7B. Самообновление апдейтера («лаг в одну версию»)

**Проблема.** `gateway-update.sh` обновляет в том числе САМ СЕБЯ, но делал это в
середине наката. Значит весь накат выполнялся **старым** кодом, а исправления
самого апдейтера вступали в силу только со следующего раза. Практическое
последствие: критичный фикс апдейтера (напр. самоперезаписи через `cp`, см.
2.8.1) приходилось подкладывать на машину руками до нажатия кнопки — иначе
этот же накат шёл бы по сломанному пути.

**Решение.** До того как что-либо изменить — до `lock`, бэкапа и dead-man-маркера
— тянем из канала **только** `gateway-update.sh`, сверяем с собой и, если
отличается, атомарно ставим и перезапускаемся через `exec`. Дальше накат идёт уже
под новым кодом. Вызывается из диспетчера в ветке `apply`.

Почему это безопасно:

| Свойство | Как обеспечено |
|---|---|
| Не бывает полу-состояния | происходит до любых разрушающих действий |
| Битый файл не поставится | кандидат проверяется `sh -n` перед установкой |
| Нет сети — не блокируемся | `curl` не удался → молча идём на текущей версии |
| Не зациклится | `GW_UPDATE_REEXEC=1` в окружении переживает `exec` |
| Есть что разбирать при ЧП | прежняя версия остаётся рядом как `.prev` |
| Откат не зависит от сети | `rollback` идёт **мимо** самообновления — путь восстановления обязан работать на том, что уже лежит на диске |

> Проверено пятью сценариями на реальном dash: отличающийся кандидат ставится и
> вызывает `exec`; идентичный игнорируется; `GW_UPDATE_REEXEC=1` останавливает
> повтор; недоступный канал не мешает накату; кандидат с битым синтаксисом
> отвергается, а файл на диске остаётся цел.

⚠️ Лаг снимается **начиная с версии, где появился этот механизм**. Накат НА неё
идёт ещё под старым кодом — это последний раз. Дальше апдейтер всегда исполняется
в самой свежей редакции.

## 8A. Требования к хосту (пакеты, юниты, файлы)

**Проблема, из-за которой это появилось.** Разделение «код vs состояние» (§2.1)
упускало третью категорию — **требования к самому хосту**. In-place накат синкал
`/opt/gateway`, `rootfs-overlay` и образы, но `apt`-пакеты не ставил никогда. В
результате на машинах, обновлённых по каналу (а не перепрошитых с `.img`),
отсутствовал `fail2ban`: его `jail.local` исправно приезжал в `/etc/fail2ban/`, а
демона в системе не было, и строка `systemctl restart fail2ban || true` молча
ничего не находила. Защита от перебора паролей числилась включённой, но не
работала. То же случилось бы с любым будущим host-пакетом.

Вторая грань той же проблемы: `Dockerfile` и `gateway-update.sh` держали **разные
захардкоженные списки** юнитов для `systemctl enable` — у наката список был
урезанный. Новый юнит, добавленный версией, включался бы только на свежей
прошивке.

**Решение — единый декларативный источник правды:** `gateway/host-requirements.list`.
Его читают оба потребителя, поэтому списки физически не могут разъехаться:

| Потребитель | Что делает |
|---|---|
| `linux-gw/Dockerfile` | ставит всё с нуля при сборке `.img` |
| `gateway-update.sh` → `_sync_host_requirements()` | доставляет недостающее на уже развёрнутой машине |

Формат — по строке на требование, инлайн-комментарии допустимы:

```
pkg <имя>            пакет из репозиториев Debian
pkg-docker <имя>     пакет из репозитория Docker CE (после добавления репо)
unit <имя>           systemd-юнит: должен быть enabled
timer <имя>          то же + при накате ещё и start (иначе заработал бы после ребута)
file <путь> <режим>  файл обязан существовать (создаётся пустым)
```

**Правила, заложенные в реализацию:**

1. **Ставятся ТОЛЬКО отсутствующие пакеты.** `apt-get upgrade` не вызывается
   никогда — накат шлюза не должен превращаться в обновление всей ОС.
2. **Файлы-предпосылки создаются ДО установки пакетов.** Демон может стартовать
   прямо из `postinst`, а жиле `[gateway-panel]` нужен существующий
   `/var/log/panel-auth.log`, иначе она не поднимется. При загрузке этот файл
   создаёт `gateway-init.sh`, но при накате boot-time юниты не переисполняются —
   поэтому требование продублировано декларативно.
3. **Провал установки НЕ откатывает накат.** Пакеты аддитивны, а код и образы к
   этому моменту уже рабочие: недоступное зеркало Debian — не повод терять
   исправную версию. Недостача не теряется: `gateway-selfcheck.sh` отдаёт её как
   **SOFT** `WARN pkg:host-requirements`, видимый в панели.
4. **Вызывается после синка `/opt/gateway`** (файл требований приезжает оттуда) и
   **до** подкладывания конфигов `fail2ban` — чтобы демон уже существовал.

> Проверено вживую на Debian 12 (`/bin/sh` = dash): на корректно собранной машине
> детектор даёт **ноль** недостающих пакетов, то есть на здоровом шлюзе накат не
> полезет ставить ничего лишнего.

## 9. Самодиагностика (health-gate)

Скрипт `gateway-selfcheck.sh` — **только read-only проверки**, никакой мутации
пользовательских данных. Переиспользуем подходы из `linux-gw/test/`.

Минимальный набор (все должны пройти за таймбокс):
- [ ] контейнеры `gw-awg`/`gw-dnsmasq`/`gw-webui` — `running`;
- [ ] туннель: `awg0` поднят, `latest-handshake` свежий (< 180с);
- [ ] **endpoint не через awg0** (нет петли) и **в main нет широких маршрутов**
      `/1../7` (регресс-проверка на баг защиты туннеля);
- [ ] панель: `curl -sf http://127.0.0.1:8000/login` → 200;
- [ ] DNS: резолв тестового домена через dnsmasq;
- [ ] forwarding: правила `MASQUERADE` на `awg0` и `MSS clamping` на месте;
- [ ] ACL/правила применились (ipset-наборы существуют, цепочка `GW_ACCESS` есть);
- [ ] `rules.json` валиден и не пуст (состояние не потерялось при накате).

Любой провал → `[ROLLBACK]` с указанием, какая проверка упала (это и есть
«ошибка на этапе X» в уведомлении).

## 10. Режимы обновления (3 шт.)

Хранить в `/etc/awg-setup/update-config.json` (это **пользовательская настройка** —
добавить в бэкап-список §6):

```json
{
  "mode": "manual | nightly | scheduled",
  "scheduled_time": "04:30",
  "auto_level": "all | patch",
  "channel": "upd-code"
}
```

1. **`manual`** — обновление только по кнопке во вкладке «Обновление». Шлюз лишь
   периодически проверяет наличие версии и показывает плашку «доступно vX.Y.Z».
2. **`nightly`** — автонакат ночью (дефолтное окно, напр. 04:00–05:00 локального
   времени), в случайную минуту окна, чтобы не было пиков.
3. **`scheduled`** — пользователь задаёт конкретное время (`scheduled_time`) и
   уровень (`auto_level`: все версии или только patch `X.Y.*`).

Реализация расписания — systemd timer (`gateway-update.timer`), читающий
`update-config.json`. Проверка версий — отдельным лёгким таймером (напр. раз в
6–12ч) независимо от режима наката.

> Безопасный дефолт на первый запуск: **`manual`** (максимум контроля), пользователь
> сам включает авто, когда доверяет механизму.

## 13. Безопасность

- Образы — по **digest** из подписанного (защищённого правами ветки) `manifest.json`
  → подмена контента невозможна без смены digest.
- GHCR — публичный pull (репо open-source), **креды не нужны**. Опционально
  read-only fine-grained token, если упрёмся в rate-limit API или репа станет
  приватной; хранить вне репо, в `/etc/awg-setup/` с правами 0600, вводить через панель.
- `manifest.json`/`VERSION` приходят из ветки `upd-code`, в которую пишет **только
  CI** (защитить branch protection — пуш только из Actions).

## 15. Краевые случаи и риски

- **Потеря доступа во время наката** → решается локальным откатом + dead-man switch.
- **Питание во время `[APPLY]`** → маркер `.update-inprogress` + guard на загрузке.
- **Миграция схемы `rules.json`** → бэкап ДО миграции, побайтовый откат.
- **Кончилось место** → preflight-проверка + ретеншн бэкапов/образов.
- **Параллельный запуск** → lock-файл, второй запуск отбивается.
- **GHCR недоступен** → накат не начинается (preflight), прод не трогается.
- **Образ awg почти не меняется** → digest тот же, pull быстрый (слои в кэше).

# Приложение А. Фича: раздельное туннелирование ПО УСТРОЙСТВУ

> Отдельная фича (не часть автообновления), описана здесь по просьбе. Делать
> можно независимо.

## А.1. Зачем и чем отличается от существующего

Сейчас вкладка **«Раздельное туннелирование» работает по НАЗНАЧЕНИЮ**: какие
*сайты/подсети* идут мимо VPN — для всех клиентов сразу (destination-based,
`direct.list`/`direct-cidrs.list` → §«защита туннеля»).

Эта фича — **по ИСТОЧНИКУ (per-device)**: тумблер у конкретного клиента
(например, телевизора) «Интернет напрямую (мимо VPN)». Когда включён — **весь**
трафик этого устройства идёт через обычный WAN, минуя туннель, независимо от
назначения. Полезно для ТВ/приставок (локальные сервисы, меньше задержка, обход
VPN-блокировок стриминга).

## А.2. Почему это легко ложится на текущий шлюз

- **NAT на WAN уже есть:** `-A POSTROUTING -o enp2s0 -j MASQUERADE` — обратный
  трафик прямого клиента вернётся, добавлять NAT не нужно.
- **Policy routing уже настроен:** таблица туннеля `51820` + `ip rule`. Добавляем
  одно правило для метки источника ПЕРЕД туннельным.
- **Матч по MAC уже используется** в правилах доступа (`gw-access-apply`) — берём
  тот же подход.

Текущие правила (для контекста):
```
32764: from all lookup main suppress_prefixlength 0
32765: not from all fwmark 0xca6c lookup 51820   ← сюда уходит трафик в туннель
32766: from all lookup main
```

## А.3. Механизм

Метим трафик устройства по **MAC** (устойчиво к смене IP) и заворачиваем в таблицу
`main` (WAN) правилом с приоритетом **раньше** туннельного (`32765`):

```sh
# пометить весь трафик от устройства (в mangle PREROUTING, до выбора маршрута)
iptables -t mangle -A PREROUTING -m mac --mac-source <MAC> -j MARK --set-mark 0x1
# маркированное — в main (там default via WAN), раньше туннельного правила
ip rule add fwmark 0x1 lookup main pref 32763
```

- `pref 32763 < 32765` → маркированный пакет резолвит дефолт через WAN и НЕ доходит
  до туннельного правила. Немаркированные клиенты идут как раньше — в туннель.
- Метка `0x1` **не конфликтует** с wg-меткой `0xca6c`.
- На сам шлюз, туннель и других клиентов — **ноль влияния** (матч строго по MAC).
- MAC-матч работает только для L2-локальных клиентов (br-lan) — это наш случай.

## А.4. Данные и хранение состояния

Список «прямых» устройств — **часть `rules.json`** (а не отдельный файл), чтобы он
автоматически попадал в бэкап §6 и переживал обновления. Например, расширить
структуру хоста флагом:

```json
{ "hosts": [ { "mac": "aa:bb:cc:dd:ee:ff", "name": "ТВ гостиная",
              "ip": "192.168.88.150", "direct": true } ] }
```

webui при сохранении генерит плоский файл для шелла (как уже делает для
`access-*`): `/etc/awg-setup/filter/direct-clients.txt` — по одной MAC в строке.

> Рекомендуется закрепить за устройством **статический IP** (в проекте есть
> `reservations.conf`) — удобнее в списке и для проверок, хотя маршрутизация и так
> по MAC.

## А.5. Скрипт `gw-direct-clients.sh`

> `linux-gw/gateway/awg/gw-direct-clients.sh` → в контейнере `gw-awg`
> (host-network, privileged — правит host iptables/ip rule). Идемпотентен:
> каждый раз полностью пересобирает свои правила. Зовётся из webui при изменении +
> из `vpn-watchdog` (рефреш), как `gw-access-apply`.

```sh
#!/bin/sh
# Per-device split tunneling: перечисленные MAC ходят НАПРЯМУЮ (мимо VPN).
LIST=/etc/awg-setup/filter/direct-clients.txt
WLOG=/var/log/awg-watchdog.log
MARK=0x1
PREF=32763
CHAIN=GW_DIRECT          # своя цепочка в mangle PREROUTING, чтобы чисто пересобирать
_log(){ printf '%s gw-direct: %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >> "$WLOG"; }

# 1) ip rule (одно, идемпотентно): маркированное → main, раньше туннельного.
ip rule list | grep -q "fwmark $MARK lookup main" \
    || ip rule add fwmark $MARK lookup main pref $PREF

# 2) Пересобираем цепочку меток с нуля.
iptables -t mangle -N "$CHAIN" 2>/dev/null
iptables -t mangle -F "$CHAIN"
iptables -t mangle -C PREROUTING -j "$CHAIN" 2>/dev/null \
    || iptables -t mangle -I PREROUTING 1 -j "$CHAIN"

n=0
if [ -f "$LIST" ]; then
    while IFS= read -r mac; do
        mac=$(printf '%s' "$mac" | tr -d ' \t\r')
        [ -n "$mac" ] || continue
        case "$mac" in \#*) continue ;; esac
        case "$mac" in
            [0-9A-Fa-f]*:*:*:*:*:*) ;;     # грубая валидация MAC
            *) continue ;;
        esac
        iptables -t mangle -A "$CHAIN" -m mac --mac-source "$mac" -j MARK --set-mark $MARK
        n=$((n+1))
    done < "$LIST"
fi
_log "применено прямых устройств: $n"

# 3) Если список пуст — правило ip rule можно снять (трафик никто не метит).
[ "$n" -eq 0 ] && ip rule del fwmark $MARK lookup main pref $PREF 2>/dev/null
exit 0
```

> Снятие при выключении тумблера: webui убирает MAC из файла и зовёт скрипт —
> цепочка пересобирается без этого MAC, устройство возвращается в туннель.

## А.6. UI

В разделе «Подключённые устройства» у каждого клиента — тумблер **«Мимо VPN»**.
Включил → MAC попадает в `rules.json.hosts[].direct=true` → генерится
`direct-clients.txt` → `docker exec gw-awg gw-direct-clients`. Рядом — индикатор
текущего внешнего IP устройства (для наглядности «вышел не через VPN»).

## А.7. Краевые случаи

- **Блокировки доступа всё равно работают.** REJECT-правила (`gw-access-apply`)
  висят в `FORWARD` и применяются независимо от маршрута — заблокированный сайт
  останется заблокированным даже для «прямого» устройства.
- **Реальный IP светится.** Прямой клиент выходит под адресом провайдера, не под
  VPN — это и есть цель для ТВ, но осознанно (не для приватного трафика).
- **DNS.** Устройство продолжает резолвить через dnsmasq шлюза — это нормально;
  на маршрутизацию не влияет (метим весь трафик по источнику).
- **Перезагрузка/рестарт контейнера.** Правила в host-namespace; на всякий случай
  рефреш из `vpn-watchdog` (как для `gw-access-*`) восстановит их идемпотентно.
- **Метка/приоритет.** `0x1` и `pref 32763` — проверить на отсутствие коллизий,
  если позже появятся другие mangle-метки; вынести в константы.

## А.8. Чеклист реализации (мини)

- `linux-gw/gateway/awg/gw-direct-clients.sh` + `COPY` в `awg/Dockerfile` +
  `chmod +x` (как `gw-access-apply`).
- webui `main.py`: поле `direct` у хоста, генерация `direct-clients.txt` в
  `_write_plan_files`, вызов `gw-direct-clients` в фоне (рядом с `gw-access-*`).
- `vpn-watchdog.sh`: добавить `docker exec gw-awg gw-direct-clients` в рефреш.
- webui фронт: тумблер «Мимо VPN» в списке устройств.
- Состояние уже в `rules.json` → отдельный бэкап не нужен (покрыт §6/§6A).

# Приложение Б. Управление железом (выключить/перезагрузить)

> Отдельная мини-фича: кнопки в панели для перезагрузки и выключения шлюза.

## Б.1. Возможно ли
Да. Контейнер `gw-webui` запущен с `pid: host` + `privileged: true` и уже ходит в
host-shell через `nsenter` (веб-консоль). Значит может отдать команду хосту:
```sh
nsenter -t 1 -m -u -i -n -p -- systemctl reboot
nsenter -t 1 -m -u -i -n -p -- systemctl poweroff
```

## Б.2. Кнопки
- **Перезагрузить** — относительно безопасно: шлюз вернётся сам через ~1–2 мин
  (туннель/панель поднимутся автоматически). Управление через туннель на это время
  пропадёт и восстановится.
- **Выключить** — ⚠ **опасно для удалённого управления**: после выключения попасть
  на шлюз можно только **физически** (или через IPMI/розетку с управлением). Удалённо
  ты его больше не включишь. Для девайса, которым рулят через его же VPN, это
  «выстрел по доступу».

## Б.3. Обязательные предосторожности
- **Подтверждение** обоих действий (модалка с явным текстом).
- Для **«Выключить»** — усиленное подтверждение (ввод имени/чекбокс «понимаю, что
  включу только физически»), либо вообще прятать за «расширенным режимом».
- Корректное завершение: дать compose-стеку остановиться (`systemctl` это сделает
  через юниты), не «дёргать питание».
- Записать действие в **журнал событий** (кто/когда инициировал).
- Доступ — только аутентифицированному админу панели.

## Б.4. Реализация (мини-чеклист)
- `main.py`: `POST /api/system/reboot`, `POST /api/system/poweroff` (с проверкой
  сессии и флага подтверждения в теле запроса).
- Команда через `nsenter -t 1 ... systemctl reboot|poweroff`.
- Фронт: две кнопки в разделе «Система»/настройках + модалки подтверждения.
- (Опционально) кнопка **«Перезапустить сервисы»** — мягче, чем reboot:
  `cd /opt/gateway && docker compose restart` (без перезагрузки ОС).

## Б.5. Решение (согласовано)
Делаем **все 4 действия**: «Перезагрузить шлюз», «Перезапустить сервисы»,
«Выключить». **Выключение — нужная фича** (не прячем), но оставляем усиленное
подтверждение (явный текст «включить можно будет только физически»). Все действия —
только для авторизованного админа + запись в журнал событий.

# Приложение В. DHCP: стратегия аренд, авто-резервирование, чистка пула

> Здесь — ответ на вопросы по DHCP и разбор «резервирование = VLAN?» (нет).

## В.1. Как раздаётся сейчас
- `dhcp-range=192.168.88.10,192.168.88.250,24h` — пул ~240 адресов, аренда **24ч**.
- DNS клиентам = сам шлюз (`dhcp-option=6,192.168.88.1`) — чтобы работали фильтр/блок.
- **Вечный адрес** по MAC = панель пишет `dhcp-host=MAC,IP[,name]` в
  `reservations.conf` (фича «Резервирование адресов и имена» — это ручная настройка).

Сейчас пул **самоочищается**: ушло устройство → через 24ч аренда истекла → IP
вернулся в пул. То есть «засирания» по сути нет, но и IP у устройства не вечный.

## В.2. Идея «выдавать на постоянку + чистить через 90 дней неактивности»

Есть два пути — от простого к гибкому.

### Вариант A (рекомендую): длинная аренда = 90 дней «бесплатно»
Просто `dhcp-range=...,90d`. Что получаем:
- устройство держит **тот же** IP, пока появляется в сети (dnsmasq и так отдаёт
  тому же MAC тот же адрес и продлевает аренду при активности);
- если устройство не продлевало аренду **90 дней** (выключено/ушло) — аренда
  истекает, IP **автоматически** возвращается в пул.

То есть «не активен 90 дней → очистить» получается **нативно**, без кода: «не
активен» в терминах DHCP = «не продлевал аренду» = выключен/отключён. Один
параметр — и цель закрыта.

> Тонкость: устройство, которое включено, но «молчит», аренду всё равно продлевает
> (DHCP renew по таймеру) — оно НЕ будет вычищено. Под «неактивностью 90 дней»
> понимается реальное отсутствие в сети, а не тишина в трафике. Обычно это и нужно.

### Вариант Б (гибче): авто-резервирование каждого устройства + janitor
Если хочется, чтобы **каждый** новый девайс сразу попадал в список как именованная
резервация (а не просто держал аренду):
1. `dhcp-script`-хук dnsmasq на события `add/old/del` пишет «last-seen» по MAC
   (timestamp) в файл-БД (плоский, как остальное состояние).
2. При первом подключении — авто-создаём запись хоста в `rules.json`
   (`mac,ip,name=hostname`), при желании сразу `reserved=true` → `dhcp-host=`.
3. **Janitor** (таймер раз в сутки): удаляет записи/резервации, у которых
   last-seen старше **90 дней** → IP освобождается, список не пухнет.

Вариант Б даёт «всё видно и поименовано + чистка», но это уже код (хук + janitor +
расширение `rules.json`). Вариант A решает «не засирать пул» одной строкой.

> Рекомендация: начать с **A** (lease=90d). Перейти к **Б** только если реально
> нужно авто-резервирование всех устройств с именами.

### Состояние/бэкап
`reservations`/`hosts` и так в `rules.json` (покрыто §6/§6A). Файл last-seen для
варианта Б — добавить в бэкап-список §6, либо считать эфемерным (восстановится из
активности после рестарта).

## В.3. Резервирование адресов и имена — это НЕ VLAN

Коротко: **через резервирование DHCP виланы настроить нельзя.** Это разные слои.

- **DHCP-резервирование (`dhcp-host`)** — статическая привязка `MAC → IP + имя`
  **внутри одной сети** (`br-lan`, один L2-сегмент / широковещательный домен).
  Это адресация, не сегментация.
- **VLAN** — это разделение на **уровне L2** (802.1Q-теги, отдельные
  широковещательные домены), настраивается на **мосту/интерфейсах**, а не в dnsmasq:
  например bridge VLAN filtering на `br-lan` или sub-интерфейсы (`br-lan.10`,
  `br-lan.20`), плюс изоляция трафика между виланами на фаерволе.

Связь между ними только такая: **сначала создаёшь VLAN** (сетевой слой), **потом**
dnsmasq обслуживает каждый VLAN своим `dhcp-range` (через `interface=`/`tag:`).
То есть резервации живут *внутри* VLAN, но не создают его.

> **VLAN — это отдельная, более крупная фича** (bridge VLAN filtering + несколько
> dhcp-range + межвилановая изоляция в iptables). Если нужна — оформим отдельным
> проектным разделом; в рамках «резервирование адресов и имена» она не делается.

## В.4. VLAN и обновления — да, DHCP придётся переосмыслить (и это правильно)

Интуиция верна: **с VLAN нельзя оставить DHCP-конфиг как сейчас**, иначе каждое
обновление будет затирать виланы. Но это не новая проблема — это ровно тот же
принцип **«код vs состояние»**, на котором стоит весь апдейт-дизайн (§2).

### Почему сейчас VLAN бы «проёбывался»
Сегодня конфиг DHCP **расщеплён**:
- **базовый кусок зашит в ОБРАЗ** (`gateway/dnsmasq/dnsmasq.conf`: `interface=br-lan`,
  единственный `dhcp-range`, опции) — это **КОД**;
- **динамика идёт из СОСТОЯНИЯ** (`reservations.conf`, `block.conf` через
  `conf-dir=/etc/dnsmasq.d/filter`) — это **состояние**, переживает обновления.

Если описание виланов (какие есть, их подсети, range, шлюзы, изоляция) положить в
**образ** — обновление, которое заменяет код, **снесёт твою топологию**. Вот он,
названный тобой риск.

### Решение: топология сети/DHCP = СОСТОЯНИЕ, а не код
Переносим всё «что настроил пользователь» из baked-образа в **генерируемый из
состояния** конфиг — как уже сделано для `gw-access-*`:
1. **Хранилище:** виланы в `rules.json` (или отдельный `network.json` в
   `/etc/awg-setup/`) — структура: `{vlan_id, name, subnet, dhcp_range, gateway_ip,
   isolated}`.
2. **Генератор-apply** (новый скрипт, как `gw-access-apply`) из этого состояния
   собирает:
   - **L2:** VLAN-интерфейсы / bridge VLAN filtering (`br-lan.10`, `br-lan.20`…) —
     сейчас (если вообще есть) это в `rootfs-overlay` = код → переносим в генерацию;
   - **DHCP:** по `dhcp-range` на каждый VLAN — пишем в `/etc/awg-setup/...`,
     dnsmasq подхватывает через `conf-dir` (НЕ хардкодим в образном `dnsmasq.conf`);
   - **изоляция** между виланами — iptables, уже знакомый паттерн `gw-access-apply`.
3. **Бэкап §6/§6A** покрывает состояние → виланы **переживают и обновление, и откат**.
4. **Обновление** меняет только **логику генератора** (код), а **топологию**
   (состояние) не трогает — как reservations и access-правила сегодня.

### Что конкретно «вынести из образа в состояние»
| Сейчас (код, в образе) | Должно стать (состояние → генерация) |
|------------------------|--------------------------------------|
| единственный `dhcp-range` в `dnsmasq.conf` | `dhcp-range` на каждый VLAN, из `network.json` через `conf-dir` |
| статический `interface=br-lan` | список интерфейсов/виланов из состояния |
| L2-настройка моста (если в rootfs) | bridge VLAN filtering из состояния |
| — | межвилановая изоляция iptables (apply-скрипт) |

### Миграция и совместимость
- При первом запуске текущий единственный `br-lan` становится «VLAN по умолчанию»
  в состоянии (как `split-default.json` подсевается на свежем шлюзе) — ничего не
  ломается, просто топология переезжает в управляемое состояние.
- Лиз 90d (вариант A, §В.2) совместим: это просто параметр per-`dhcp-range`.

### Вывод
VLAN не требует «переделать DHCP с нуля» — требует **сдвинуть границу код/состояние**:
сетевую топологию (включая DHCP-ranges) сделать состоянием, управляемым из панели и
генерируемым apply-скриптом. После этого виланы автоматически устойчивы к
обновлениям. Это предпосылка к VLAN-фиче — лучше заложить её в DHCP-рефактор
**до** того, как браться за сами виланы.

> Когда созреешь до VLAN — оформлю отдельным проектным разделом (L2-модель,
> межвилановый фаервол, UI). Здесь зафиксирована только архитектурная развилка.

# Приложение Г. Сегментация сети / VLAN (проектный разбор)

> Предпосылка — DHCP-рефактор «топология → состояние» (§В.4). Фича DHCP
> (резервирование/имена) остаётся как есть; VLAN строится поверх.

## Г.1. Две модели — честно про железо

Ключевая развилка, которая определяет ВСЁ остальное:

| | **Политики-группы (L3)** | **Настоящие VLAN (L2)** |
|---|---|---|
| Что разделяет | маршрутизацию/политику/фаервол | + физическую изоляцию L2 |
| Нужно железо | нет, только шлюз | **managed-свитч и/или VLAN-aware точки** |
| Изоляция | по подсети+MAC на L3 (egress, межгрупповой фаервол) | полная (разные broadcast-домены, 802.1Q) |
| Слабое место | юзер со статик-IP может влезть в чужую подсеть (но egress ты всё равно рулишь) | требует инфраструктуры |

**Важная правда:** на одном «тупом» свитче, висящем на одном порту шлюза, **настоящую
L2-изоляцию сделать нельзя** — все в одном broadcast-домене. Для реальных VLAN
нужны managed-свитч / VLAN-aware AP (802.1Q-транк в шлюз, sub-интерфейсы
`br-lan.10`, `br-lan.20`…). У шлюза есть **свободный NIC `enp4s0`** — его можно
отдать под транк/второй сегмент.

**Рекомендация:** делаем **единую модель данных и UI** (имена, подсети, egress,
комментарии, карта), а **enforcement** — двухуровневый:
1. **L3-политики** (egress/изоляция по подсети+MAC) — работает уже сейчас, на любом
   железе. Закрывает «этот через интернет, этот через VPN, этому только локалка».
2. **L2-теги 802.1Q** — включаются, когда в офисе есть managed-свитч/AP. Апгрейд
   изоляции, та же модель данных.

Так продукт работает у всех, а у кого есть managed-железо — получают полную изоляцию.

> Контекст: в офисе как минимум Wi-Fi роутер, наличие managed-свитча/VLAN-aware
> точек неизвестно. Поэтому **не блокируемся** на managed-железе: запускаем
> L3-политики (работают и за обычным Wi-Fi роутером), а 802.1Q закладываем
> архитектурно как апгрейд — модель данных и UI к нему уже готовы.

## Г.2. Статическая адресация — частично согласен, но не «всё подряд»

Тезис «в VLAN адреса жёстко за устройствами» — правильная **половина**. Уточняю:
- Жёстко привязывать стоит **членство в VLAN по MAC** (`MAC → VLAN`), а не
  обязательно `MAC → точный IP`. Именно членство разделяет логику детерминированно.
- **Внутри** VLAN адреса можно раздавать DHCP-динамикой из диапазона этого VLAN, а
  статические резервации (текущая фича `dhcp-host`) держать только для того, что
  правда требует стабильного IP: серверы, принтеры, NAS, то что фильтруешь по IP.
- Пиновать IP **каждому** клиенту офиса вручную — лишний труд и ошибки. VLAN и так
  разделяет логику (своя подсеть + свой egress + фаервол); точный IP для этого не
  нужен.

Итого: **жёсткое = MAC→VLAN**, адрес внутри VLAN — DHCP + резервации по необходимости.

## Г.3. Адресное пространство — /24 мало, и 10.0.0.0/8 НЕЛЬЗЯ

`192.168.88.0/24` = 254 адреса — для офиса с несколькими сегментами мало.

**Почему `10.0.0.0/8` отпадает.** Туннель маршрутизирует фактически весь трафик
(AllowedIPs ≈ `0.0.0.0/0`), а **VPN-сервер раздаёт адреса в `10.x`** — там живут
ресурсы на той стороне VPN. Если локальный VLAN взять из `10.x`, его connected-
маршрут (`/24` на интерфейсе) перекроет более общий туннельный путь → до VPN-
ресурсов в той же `10.x` **перестанут доставать**. Поэтому `10.0.0.0/8` — табу.

**Также не пересекаемся со служебным:** туннель `10.13.13.0/24`, docker
`172.17.0.0/16`, WAN `192.168.0.0/24`, текущий LAN `192.168.88.0/24`.

**Рекомендация — чистые большие пулы (можно совмещать, «чем больше, тем лучше»):**

| Пул | Размер | Почему годится |
|-----|--------|----------------|
| **`100.64.0.0/10`** (CGNAT, RFC 6598) | **~4.19 млн** | не RFC1918, VPN/офисные роутеры его не раздают, не коллизит с `10.x` |
| `172.16.0.0/12` **минус** `172.17.0.0/16` | ~1.05 млн | приватный, докер-кусок исключаем |

- **Основной — `100.64.0.0/10`** (самый большой чистый блок). Нарезка по VLAN:
  `100.64.<vlan>.0/24` (VLAN 10 → `100.64.10.0/24`…). Префикс настраиваемый
  (`/24` по умолчанию; `/23`, `/22`, `/16` под большие сегменты).
- `172.16.0.0/12` (кроме `172.17`) — как дополнение/альтернатива.
- На офис из сотен машин этого с огромным запасом (тысячи VLAN по /24).

> Сетевой guard защиты туннеля (§«защита туннеля») трогать не нужно: он про
> **destination**-маршруты «напрямую», а VLAN — это **source**-политика. Конфликта
> нет. Нужно лишь NAT-ить каждую VLAN-подсеть на её egress (WAN или awg0).

## Г.4. Egress (3 тумблера) + межсегментный доступ

Здесь ключевая мысль: **«куда можно ВЫХОДИТЬ» и «кто может ДОСТУЧАТЬСЯ» — это две
РАЗНЫЕ оси.** Кейс 1С это прямо показывает (см. ниже). Поэтому два независимых
блока настроек.

### (а) Egress — 3 тумблера (как просил)
У каждого VLAN (и, как частный случай, устройства — Приложение А) ровно один режим
исходящего трафика в внешний мир:

| Тумблер | Что значит | Реализация |
|---|---|---|
| **Разрешить VPN** | весь внешний трафик через туннель (как сейчас) | дефолт; отдельное правило не нужно |
| **Только интернет** | через WAN, мимо VPN | `ip rule from <subnet> lookup main` раньше туннельного |
| **Только локальная сеть** | наружу НИКУДА (ни VPN, ни интернет) | фаервол: DROP forward в `enp2s0`/`awg0` |

### (б) Межсегментный доступ — отдельно от egress
- Флаг **`isolated`**: по умолчанию VLAN не видит чужие сегменты (DROP в FORWARD
  между vlan-интерфейсами).
- **Исключения-«общие ресурсы»**: хост/VLAN можно пометить «доступен из всех
  сегментов» (или из выбранных) — ALLOW в FORWARD к нему, даже если он `isolated`
  и `lan-only`. Это и закрывает кейс 1С.

### Разбор кейса 1С (важный)
> Сервер 1С: в интернет ему НЕЛЬЗЯ (ни VPN, ни WAN), работает только в локалке, но
> **доступ к нему нужен всем**.

Раскладывается ровно на две оси:
- **egress = «Только локальная сеть»** → сам сервер наружу не ходит;
- **reachable_from = all** → все сегменты могут открыть соединение К нему.

То есть: ставим серверу (или его сегменту «Серверы») egress=`lan-only` +
`isolated`, и помечаем его «доступен всем». Генератор кладёт в FORWARD: ALLOW
`* → 1С:нужные порты`, DROP `1С → enp2s0/awg0`. Сервер заперт от интернета, но
виден всем. Если позже понадобится «1С только бухгалтерии» — меняем `all` на
список сегментов, та же механика.

> Всё это — знакомые механизмы (policy routing + iptables), генерируются
> apply-скриптом из состояния. Никакой новой магии — только две оси вместо одной.

## Г.5. Модель данных (состояние, §В.4)

Отдельный `network.json` в `/etc/awg-setup/` (покрыт бэкапом §6/§6A). Две оси:
`egress` (vpn|direct|lan_only) и доступ (`isolated` + `reachable_from`):
```json
{
  "vlans": [
    { "id": 10, "name": "Бухгалтерия", "comment": "рабочие ПК",
      "subnet": "100.64.10.0/24", "gateway": "100.64.10.1",
      "dhcp_range": ["100.64.10.50", "100.64.10.250", "90d"],
      "egress": "vpn", "isolated": true, "reachable_from": [],
      "members": ["aa:bb:cc:dd:ee:01", "aa:bb:cc:dd:ee:02"] },

    { "id": 20, "name": "Гостевой", "comment": "телеки, гости",
      "subnet": "100.64.20.0/24", "egress": "direct", "isolated": true },

    { "id": 30, "name": "Серверы (1С)", "comment": "БД 1С, без интернета",
      "subnet": "100.64.30.0/24",
      "egress": "lan_only",          // сам наружу никуда
      "isolated": true,
      "reachable_from": "all"        // но достучаться к нему могут все
    }
  ]
}
```
- `egress`: `vpn` (туннель, дефолт) | `direct` (WAN) | `lan_only` (наружу никуда).
- `isolated`: по умолчанию не видит чужие сегменты.
- `reachable_from`: `"all"` | список `id` сегментов, кому разрешён доступ К нему
  (общие ресурсы вроде 1С), даже при `isolated`+`lan_only`.

Генератор (`gw-network-apply`, новый, в стиле `gw-access-apply`) из него собирает:
L2 (sub-интерфейсы/bridge VLAN filtering), dnsmasq `dhcp-range` на VLAN (через
`conf-dir`), `ip rule` egress, NAT на egress, FORWARD-правила доступа (изоляция +
исключения `reachable_from`).

## Г.6. Графическая карта сети (UI)

- **Карта:** шлюз в центре → VLAN-узлы (карточки) → устройства. На карточке: имя,
  комментарий, подсеть, иконка egress (🌐 direct / 🛡 VPN / 🔒 lan-only),
  счётчик устройств, флаг изоляции.
- **Действия:** создать/переименовать VLAN, комментарий, перетащить устройство в
  другой VLAN (меняет `MAC→VLAN`), задать egress/изоляцию.
- **Фазировка:** сначала **таблица/список** VLAN (быстро, всё управляемо), карту —
  вторым этапом (это заметный объём фронта; можно SVG/canvas или лёгкая либа).

## Г.7. Связь с остальным

- **Приложение А** (per-device direct) — частный случай per-VLAN egress; после
  VLAN можно оставить как «быстрый тумблер для одного устройства» либо влить в VLAN.
- **Резервации/имена** — живут внутри VLAN, не отменяются.
- **NAT** — на каждый egress своя MASQUERADE-цепочка по source-подсети VLAN.
- **Автообновление** — топология в состоянии (§В.4) → VLAN переживают апдейт/откат.

## Д.4. Журнал событий ЖИВ, но 5-мин watchdog / 1-мин sysmon на этом боксе спят

Уточнение после перепроверки (важно не путать две вещи):

**Журнал событий работает — это факт.** Панель `/api/logs` читает
`/var/log/awg-watchdog.log`; `mtime` файла свежий (запись в HH:20 сегодня).
Питают его сейчас **поток webui** (часовой авто-перерезолв в HH:20 + действия в
панели: вход в консоль, смена конфига и т.п.) — это и есть «логи, которые сыпятся».

**Но конкретно периодика watchdog/sysmon на ЭТОМ боксе не тикает** (замеры от systemd):
- `awg-watchdog.timer` / `sysmon.timer`: `ActiveState=inactive`, `LastTriggerUSec=`
  **пусто** (за загруз ни разу не срабатывал);
- на хосте нет процесса-петли `vpn-watchdog`/`sysmon`;
- внутри контейнеров `crond` есть только в `gw-webui`, но `/etc/periodic/*` **пустые** —
  gateway-задачи через Docker-cron тоже не планируются;
- косвенно: `gw-access-apply` логировался бы каждые 5 мин, если бы watchdog тикал —
  в логе же часовые промежутки (только webui-авторезолв).

**Почему это легко спутать:** журнал общий, в него пишет много источников (webui,
awg-up при старте, авторезолв, изредка ручной прогон), поэтому он выглядит живым —
но это НЕ значит, что 5-мин failover-watchdog и 1-мин sysmon реально крутятся.

**ПОДТВЕРЖДЕНО журналом событий владельца.** В выгрузке журнала: только
загрузочные сервисы (две перезагрузки — 09:03 и 10:53), часовой авто-перерезолв
(webui, HH:20), ручное тестирование фикса (08:2x) и действия в панели. **Ни одной**
строки `VPN down`/`VPN restored`/`fallback` (vpn-watchdog) и **ни одной** от sysmon;
`OK gw-access-apply` встречается только в ручном кластере, а не каждые 5 мин (хотя
watchdog зовёт его безусловно каждый прогон). Вывод однозначный: на этом боксе
5-мин watchdog и 1-мин sysmon не работают.

**Важно для ТЗ:** авто-обновление (dead-man switch, health-gate) и рефреш VLAN/ACL
**рассчитывают, что таймеры включены**. Поэтому инсталлятор/апдейтер должен
`enable --now` свои таймеры и проверять это в self-check (§9). На проде ничего не
трогал — включение watchdog/sysmon твоё решение.

### Д.4a. Баг журнала: рассинхрон времени контейнер↔хост
В журнале метки времени «прыгают на 3 часа»: контейнеры (`gw-awg`, `gw-webui`)
пишут в **UTC**, хост-сервисы — в **MSK**. Пример: строка webui `10:20:42` — это
`13:20:42 MSK` (совпадает с `mtime` файла). Журнал событий из-за этого выглядит
нарушенным по порядку и вводит в заблуждение. **Фикс:** прокинуть контейнерам тот
же `TZ`/`/etc/localtime`, что у хоста (auto-tz уже определяет пояс) — единое время
во всём журнале. Мелочь, но для продукта важная (диагностика по журналу).

## Д.6. Принцип железо-агностичности (формализуем для ВСЕХ новых фич)
Закрепляем как требование ТЗ (то, что просил — «заменил на 1 Гбит, ничего не
поменялось»):
1. **Никаких имён интерфейсов в коде/состоянии-топологии.** Имена берутся из
   runtime-детекта (`wan-detect.sh`-паттерн), а конфиг оперирует **ролями**
   (WAN/LAN/VLAN-id), не `enpXsY`.
2. **Число карт — переменная.** 2, 4, 8 портов — генератор раскидывает по ролям/
   VLAN из состояния; нет портов под VLAN → деградируем в L3-политики на одном
   мосту (не падаем).
3. **Скорость/драйвер — не важны.** Нигде не завязываемся на 100/1000.
4. **NAT/egress — по детектированному `$wan`**, не по имени.
5. **Self-check (§9)** проверяет инвариант: WAN определён, LAN-мост есть, форвардинг
   включён — независимо от того, какие это физически карты.
