# Архитектура

[← К содержанию](README.md)

Документ описывает, из чего собран Gateway Linux, как устроены слои системы и
как трафик идёт от провайдера к устройству.

---

## 1. Слои системы

```gw-diagram layers
```

Хост содержит только ОС, драйверы и управляющие скрипты. Вся «полезная нагрузка»
вынесена в три Docker‑контейнера в режиме `network_mode: host` — они видят
сетевые интерфейсы хоста напрямую (`br-lan`, `awg0`, WAN‑порт).

---

## 2. Контейнеры (Docker‑сервисы)

| Контейнер | База | Роль | Привилегии |
|-----------|------|------|-----------|
| **gw-awg** | Alpine | Туннель AmneziaWG (`amneziawg-go`), маршрутизация обхода, ipset+iptables ACL | `privileged` |
| **gw-dnsmasq** | Alpine | DHCP‑сервер LAN (192.168.88.10–250), DNS, DNS‑блокировки | `NET_ADMIN` |
| **gw-webui** | Python‑slim | Веб‑панель: FastAPI (uvicorn) + nginx (HTTPS) | `privileged`, `docker.sock` |

Образы контейнеров **вшиты в `.img`** (`/opt/gateway/images.tar`) и грузятся через
`docker load` при первом старте — на целевом ПК ничего не компилируется.

---

## 3. Хост‑скрипты (systemd)

| Скрипт / сервис | Когда | Что делает |
|-----------------|-------|-----------|
| `gateway-installer` | загрузка с USB | меню установки на диск / live‑режим |
| `gateway-growroot` | каждый старт | растит корневой раздел на весь диск |
| `gateway-swap` | первый старт | swap‑файл 2×RAM (OOM‑страховка) |
| `gateway-init` | каждый старт | IP‑форвардинг, TUN, дефолты |
| `wan-detect` | каждый старт | находит WAN‑порт по наличию интернета, строит `br-lan`, NAT |
| `gateway-load-images` | каждый старт | `docker load` вшитых образов |
| `gateway-compose` | каждый старт | поднимает контейнеры |
| `vpn-watchdog` | каждые 5 мин | failover VPN + рефреш маршрутов обхода и ACL |
| `sysmon` | каждую минуту | рестарт упавших сервисов, чистка памяти |
| `auto-timezone` | старт | часовой пояс по гео‑IP (через WAN, мимо VPN) |
| `client-traffic` | сервис | побайтовый учёт скорости по клиентам |

---

## 4. Поток трафика

```gw-diagram traffic
```

**Ключевой принцип:** загруженный VPN‑ключ нормализуется в `AllowedIPs = 0.0.0.0/0`
— весь трафик по умолчанию идёт в туннель. **Маршрутизацией рулит сам шлюз**, а не
ключ: адреса из списка «раздельного туннелирования» получают более специфичный
маршрут через WAN (мимо VPN). Подробнее — [VPN и раздельное туннелирование](vpn-split-tunneling.md).

---

## 5. Каталог данных

Конфигурация и правила живут в `/etc/awg-setup/` (шарится в контейнеры):

| Путь | Содержимое |
|------|-----------|
| `/etc/amnezia/awg0.conf` | активный (нормализованный) VPN‑ключ |
| `/etc/awg-setup/filter/rules.json` | группы, блокировки, хосты, split‑ресурсы |
| `/etc/awg-setup/filter/orig-config.conf` | исходный ключ (как залили) |
| `/etc/awg-setup/filter/orig-allowedips.txt` | исходный AllowedIPs (для разбора дырок) |
| `/etc/awg-setup/filter/access-sets.txt` | план: домен → ipset (для ACL) |
| `/etc/awg-setup/filter/access-rules.txt` | план: правила блокировки по MAC |
| `/etc/awg-setup/filter/direct.list` / `direct-cidrs.list` | обход: домены и подсети |
| `/etc/awg-setup/filter/reservations.conf` | DHCP‑резервы (вечные адреса) |
| `/etc/awg-setup/split-default.json` | стандартный шаблон обхода (RU) |

Веб‑панель пишет `rules.json` + плоские план‑файлы, а хелперы в `gw-awg`
(`gw-access-routes`, `gw-access-apply`) их применяют (маршруты и ipset+iptables).

---

## 6. Самовосстановление

- **При каждой загрузке** — переопределение сети (`wan-detect`), рост раздела.
- **Docker `restart: unless-stopped`** — упавший контейнер поднимается сам.
- **Неубиваемая панель** — nginx под супервизором, uvicorn авто‑рестарт, HTTP‑fallback при сбое TLS.
- **vpn-watchdog (5 мин)** — VPN упал → прямой интернет → переподнятие.
- **sysmon (1 мин)** — следит за сервисами, чистит память.

Даже если VPN‑сервер ляжет — интернет не теряется (failover на прямой канал),
и трафик вернётся в туннель, когда сервер поднимется.
