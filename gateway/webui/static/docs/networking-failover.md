# Сеть и отказоустойчивость

[← К содержанию](README.md)

Как шлюз определяет порты, раздаёт сеть, делает NAT и защищается от сбоев.

---

## 1. Определение портов (WAN / LAN)

`wan-detect.sh` при **каждой** загрузке:

1. Находит все физические Ethernet‑интерфейсы (исключая `br-*`, `docker*`,
   `veth*`, `awg*`, `wlan*`).
2. Поднимает все порты, ждёт согласования линка (до ~6 с).
3. Для каждого с активным кабелем проверяет **наличие интернета** (DHCP/статика → проба).
4. **Первый порт с интернетом → WAN.** Все остальные → мост `br-lan`.
5. Поднимает DHCP на `br-lan` (192.168.88.1) и NAT с WAN.

| Конфигурация | Результат |
|--------------|-----------|
| 2 родные сетевухи | интернет‑порт → WAN, второй → LAN |
| 2 родные + 2 пустых PCI | интернет → WAN, остальные 3 порта в мосту |
| Перевёрнутые порты | не зашит на eth0 — берёт тот, где реально интернет |
| Статический WAN | если на порту уже есть IP — использует его |
| Кабель воткнут позже | порт уже в мосту — заработает сразу |

> **RU‑дружественная проба интернета.** Поскольку `8.8.8.8` / `1.1.1.1` бывают
> заблокированы, проба идёт по нескольким целям, включая RU
> (`77.88.8.8`, `ya.ru`, `mail.ru` и др.), плюс TCP‑проверка через `curl`.

### Роли в панели «Сеть»

| Роль | Что это |
|------|---------|
| **WAN** | порт к провайдеру (вход интернета) |
| **LAN** | мост `br-lan`, IP `192.168.88.1` |
| **LAN‑порт** | физический порт — член моста `br-lan` |
| **VPN** | туннель `awg0`, IP `10.x.x.x` |

## 2. NAT и MSS (чтобы у клиентов был интернет)

| Правило | Где | Зачем |
|---------|-----|-------|
| `MASQUERADE -o awg0` | nat POSTROUTING | без него трафик клиента уходит в туннель с приватным src → VPN дропает |
| `MASQUERADE -o <wan>` | nat POSTROUTING | NAT для прямого трафика / failover |
| `TCPMSS --clamp-mss-to-pmtu -o awg0` | mangle FORWARD | туннель MTU ~1280 < LAN 1500; без клампинга большие пакеты молча теряются (особенно RU‑сайты) |

Учёт скорости по клиентам — в таблице **`mangle`** (Docker её не перестраивает,
в отличие от `filter`), цепочка `GW_ACCT`.

## 3. Защита от петель и рабочих сетей

| Защита | Что делает |
|--------|-----------|
| **Endpoint /32 + fwmark** | адрес VPN‑сервера всегда идёт через WAN, не через туннель ([подробнее](vpn-split-tunneling.md#5-endpoint-всегда-мимо-туннеля-нет-петли)) |
| **Loop‑guard** | `awg-up` проверяет, что endpoint реально не через `awg0`, иначе пишет ERR в журнал |
| **keep_direct** | служебные сети (LAN `192.168.88.0/24`, docker `172.17.0.0/16`, подсеть WAN) держатся напрямую — до панели/SSH/контейнеров всегда достучаться |

## 4. Failover VPN

```gw-diagram failover
```

Пользователь **не теряет интернет**, даже если VPN‑сервер лёг — трафик идёт
напрямую и автоматически возвращается в туннель, когда сервер поднимется.

Watchdog заодно рефрешит маршруты обхода (`gw-access-routes`) и ACL
(`gw-access-apply`) — у сайтов меняются IP.

---

## 5. Драйверы сетевых карт

- **Mainline‑ядро Debian** содержит модули почти всех Ethernet‑контроллеров
  (Realtek, Intel, Broadcom, Atheros, Aquantia, Nvidia…).
- **udev** грузит нужный модуль по PCI/USB modalias автоматически.
- **Firmware‑блобы** (Realtek, Broadcom, Intel и др.) включены в образ.

Итог: воткнул карту → ядро подняло драйвер → `wan-detect` её увидел. Поменял
железо/кабели → просто перезагрузи, порты переопределятся.
